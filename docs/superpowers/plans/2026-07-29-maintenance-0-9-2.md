### Task 1: The branch slug stops mangling an inline spec

**Files:**
- Modify: `plugins/spar/commands/ready.md:41-42`
- Modify: `adapters/codex/skills/spar-ready/SKILL.md:72-73`
- Test: `tests/test_ready_slug.sh` (new)

**Interfaces:**
- Produces: nothing importable. The slug is inline shell in two markdown documents, so the test extracts the recipe from each document and runs it — that is the only way to test a document's shell without duplicating it.

**The recipe today**, identical in both documents:

```bash
RDY_SLUG="$(printf '%s' "$RDY_SPEC" | sed 's#.*/##; s/\.[A-Za-z0-9]*$//' | tr '[:upper:] ' '[:lower:]-' | tr -cd 'a-z0-9-' | sed 's/^-*//; s/-*$//' | cut -c1-40)"
[ -n "$RDY_SLUG" ] || RDY_SLUG=run
```

**Two defects.** `s#.*/##` and the extension strip exist to turn a path into its
stem; applied to an inline description that happens to mention a path, they cut
everything before the last `/` and the name starts mid-sentence. And runs of `-`
are never collapsed — spaces become dashes, non-ASCII characters are deleted
between them, and a Korean phrase leaves `------`.

Observed: `spar/specs------spar-reportsh-reviewer------i-20260729-132605`.

**The fix.** Strip basename and extension only when `$RDY_SPEC` names an existing
file; collapse runs of `-`:

```bash
# Basename and extension stripping is for a spec that IS a file. Applied to an
# inline description it cuts everything before the last '/' the prose happens to
# contain, and the branch name starts mid-sentence.
if [ -f "$RDY_SPEC" ]; then RDY_SLUG_SRC="$(printf '%s' "$RDY_SPEC" | sed 's#.*/##; s/\.[A-Za-z0-9]*$//')"
else RDY_SLUG_SRC="$RDY_SPEC"; fi
# The squeeze matters because the ASCII filter deletes characters BETWEEN the
# dashes that spaces became: a non-Latin phrase would otherwise leave a run of
# them. Deliberately ASCII-only — git takes UTF-8 refs, but a branch name is not
# where the topic is read, and byte-safe truncation of multibyte text is
# machinery this does not need.
RDY_SLUG="$(printf '%s' "$RDY_SLUG_SRC" | tr '[:upper:] ' '[:lower:]-' | tr -cd 'a-z0-9-' | tr -s '-' | sed 's/^-*//; s/-*$//' | cut -c1-40)"
[ -n "$RDY_SLUG" ] || RDY_SLUG=run
```

`tr -s '-'` before the trim, so a name that is all dashes reduces to one and then
trims to empty and reaches the `run` fallback.

```bash
#!/usr/bin/env bash
set -uo pipefail
PASS=0; FAIL=0
ROOT="$(cd "$(dirname "$0")/.." && pwd)"
eqchk(){ if [ "$2" = "$3" ]; then echo "PASS: $1"; PASS=$((PASS+1)); else echo "FAIL: $1"; echo "  want:[$2]"; echo "  got:[$3]"; FAIL=$((FAIL+1)); fi; }

TMP=$(mktemp -d); cd "$TMP" || exit 1

# The recipe as the document actually carries it: the RDY_SLUG assignment plus
# the fallback line, and the `if [ -f ... ]` block above it once it exists.
# Extracted, never restated — a copy would pass on a broken document.
recipe() { # $1=document path → the slug lines, verbatim
  awk '/^# Basename and extension stripping/,/^\[ -n "\$RDY_SLUG" \]/' "$1"
}
slug() { # $1=document  $2=spec → the slug that document computes
  local src; src="$(recipe "$ROOT/$1")"
  [ -n "$src" ] || { echo "(no recipe found in $1)"; return 1; }
  RDY_SPEC="$2" bash -c "$src"'; printf "%s" "$RDY_SLUG"'
}

for doc in plugins/spar/commands/ready.md adapters/codex/skills/spar-ready/SKILL.md; do
  # A real file: basename and extension still stripped.
  mkdir -p docs/superpowers/specs
  : > docs/superpowers/specs/2026-07-29-a-design.md
  eqchk "$doc — a spec path keeps its stem" "2026-07-29-a-design" \
    "$(slug "$doc" docs/superpowers/specs/2026-07-29-a-design.md)"

  # Inline prose that mentions a path: NOT basename-stripped. This is the
  # observed defect — the name used to start at the last path component.
  # The retained ASCII filter DELETES '/' rather than dashing it, so the words
  # run together. That is the existing filter's behaviour and this task does not
  # change it; the point of the check is that the name still starts at "fix".
  eqchk "$doc — inline prose is not basename-stripped" \
    "fix-docssuperpowersspecs-and-the-slug" \
    "$(slug "$doc" 'Fix docs/superpowers/specs and the slug')"

  # Dash runs collapse. Non-ASCII is deleted between the dashes that spaces
  # became, so without a squeeze this leaves a run of them.
  eqchk "$doc — dash runs collapse" "spar-report-reviewer" \
    "$(slug "$doc" 'spar-report 의 reviewer 폴백')"

  # Nothing usable at all still yields a usable branch name.
  eqchk "$doc — an all-non-ascii spec falls back" "run" \
    "$(slug "$doc" '한글로만 쓴 설명')"

  # to the extension strip, since it is not a file. The '.' is deleted by the
  # ASCII filter, not turned into a dash — so "sh" survives, joined.
  eqchk "$doc — a trailing dotted word survives inline" "fix-spar-reportsh" \
    "$(slug "$doc" 'Fix spar-report.sh')"

# The two documents must agree. A mirror that drifts is the failure this repo has

eqchk "both documents compute the same slug" \
  "$(slug plugins/spar/commands/ready.md 'Fix docs/a and b')" \
  "$(slug adapters/codex/skills/spar-ready/SKILL.md 'Fix docs/a and b')"

cd /; rm -rf "$TMP"
echo; echo "PASS=$PASS FAIL=$FAIL"; exit "$FAIL"
```

- [ ] **Step 4: Add the `check` assertions**

One new item, in the shape the existing ones use (`say <n> <verdict> <detail>`,
`failed=1` on a miss, `real_file` for every artifact so a planted symlink is
reported rather than silently accepted):

- every `reviews/spar-plan-*.md` candidate is validated with the reporting
  validator whether or not a state names it, so a planted one is reported even in
  a workspace with no plan state — tamper reporting must not depend on the state.
  A regular result with no plan state at all is `FAILED`, not unanswered: the
  result is itself evidence the review ran, so the question is no longer "did you
  get to item 5" but "you did, and the plan was never activated through this
  seat". `spar-cancel` leaves exactly that shape;
- the result the plan state NAMES exists and is a regular file — read
  `plan_review_id` from the state and judge exactly
  `reviews/spar-plan-<that id>.md`. Not whichever `spar-plan-*.md` a glob returns:
  item 5 tells the human to cancel and re-run `spar-ready` when the first review
  comes back CLEAN, and `spar-cancel` keeps the results, so more than one is
  expected — and a stale one from an abandoned attempt would otherwise vouch for
  the plan that actually ran, including one started with `--no-plan-review`. An id
  that does not match the standard shape is treated as naming nothing;
- its first line matches `^PLAN-REVIEW: (CLEAN|FINDINGS)$`, with `\r` stripped —
  the same normalisation `spar-plan-review-check.sh:119` uses;
- the plan state records `author: codex` and a non-empty `owner_session`, which
  together prove activation went through the Codex seat rather than being
  hand-written.

**Absence is not failure.** `check` is documented to run before a session as
well as after, and it reports unresolved items and exits zero — item 3 already
does exactly this at `:370`, answering `NEEDS YOUR ANSWER` when a marker exists
but nothing activated. A bare absence of plan artifacts cannot tell "the human
skipped item 5" from "no session ran at all", so the new item follows the same
three-way shape:

- plan artifacts present and well-formed → `CONFIRMED`;
- present but malformed, or the plan state missing its Codex stamps → `FAILED`;
- absent while other durable evidence shows the live run happened (a round
  artifact, or a loop state whose `owner_session` matches the marker — the same
  evidence item 3 uses) → `FAILED`, because the run occurred and skipped it;
- absent with no evidence of a run → `NEEDS YOUR ANSWER`.

**An alternative considered and not taken.** The threshold above is activation,
which also fails a session still part-way through item 4 — item 5 comes after
item 4, so at that moment the item genuinely is not done yet. The narrower
alternative is to fail only once the run has *ended*, keyed on an outcome file or
a report (both written only at a terminal path), and answer `NEEDS YOUR ANSWER`
for started-but-unfinished.

Activation is what ships. `check` is documented to be run when the session is
over, so a mid-run reading is off-label, and "item 5 is not done" is a true
statement there — while the narrower rule buys nothing on the documented path and
adds a second evidence variable to keep straight. Worth revisiting only if someone
starts running `check` mid-session on purpose.

One thing the narrower rule surfaced is kept either way: `record_outcome` runs
first at every terminal path, so a rule keyed on the *report* alone would let a
run whose report writer failed escape. Fixture 9e2 pins that case.

State in the verdict text that a refusal cannot be judged from artifacts, so a
reader does not take a pass here as covering item 5's part (a).
